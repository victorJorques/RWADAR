## Claves que da Víctor

**Dos claves**, cada una con lo mínimo que usa el código y nada más. Víctor
las crea y las pega él: nunca en un chat, un archivo ni una captura. Las dos
se pegan igual: **GitHub › el repositorio › Settings › Secrets and variables
› Actions › New repository secret**, con el nombre exacto de la primera
columna en «Name» y la clave en «Secret». Los flujos nunca las enseñan, y
cada una llega solo a los pasos que la usan. **No hay clave de Cloudflare**
(decisión del 08/11/2026): el DNS lo pone a mano la sesión de Claude del PC.

| Secreto | Dónde se crea | Permisos (solo estos) | Caducidad | Lo usan |
|---|---|---|---|---|
| `SUPABASE_ACCESS_TOKEN` | supabase.com/dashboard/account/tokens › Generate new token, **con alcance** (scoped token): **solo el proyecto RWAdar, `exgpmjpaaebyoolpwced`** | **Auth Config: Read-write** y **Project Settings: Read-write**. Qué usa el código de cada una (consultado el 09/11/2026):

- **Supabase** (https://supabase.com/docs/guides/platform/personal-access-tokens):
  leer el proyecto, `GET /v1/projects/{ref}`, pide Project Settings (Read);
  leer la configuración de Auth, Auth Config (Read); cambiarla (`PATCH
  /v1/projects/{ref}/config/auth`: plantillas y SMTP), «Auth Config
  (Read-write) and Project Settings (Read-write)». Saber si se puede
  actualizar Postgres pide además **Database (Read)**, y ese permiso incluye
  «Read only query»: consultas SQL de lectura sobre **toda la base**, con
  `auth.users` (los correos de todos los registrados) y el Vault (el token de
  los avisos). Por eso **no se da**: `estado` dice que no lo mira y sigue. Si
  algún día hace falta saberlo, se crea para ese momento un token aparte, de
  caducidad corta, y se revoca al acabar.
- **Lettermint** (https://lettermint.co/docs/platform/teams/api-tokens):
  `read:team` para ver si la cuenta está verificada (`GET /team`);
  `read:projects` y `write:projects` para el proyecto, activar su SMTP y
  crear o borrar sus dos tokens; `read:domains` y `write:domains` para leer
  el dominio y pedir su verificación; `read:routes` y `write:routes` para el
  seguimiento y el enlace de baja. Su documentación dice que `write:projects`
  permite «Create, update, and delete projects and their Project API tokens»:
  es el permiso más delicado, y por eso este token no lo comparte nadie.
- **Uno por uso.** El flujo «Correo Lettermint» (`sincronizar-bajas`, que
  correría solo cada día) usa **otro** token de equipo, `LETTERMINT_TEAM_TOKEN`,
  con **solo `read:suppressions`** (contrato de avisos, punto 5.4). No es de
  estas dos claves ni hace falta para las rondas 1 y 2: se crea solo si se
  enciende la sincronización. Así, revocar uno nunca rompe el otro, y el
  trabajo que corre sin nadie delante no puede crear tokens que envíen como
  `rwadar.app`.
- `crear-token-base` usa además `SUPABASE_DB_URL`, que ya existe (el de la
  copia de seguridad): no hay que crear nada.
- Si una clave se filtra: se revoca en el mismo panel, se crea otra con los
  mismos permisos y se pega encima del secreto (mismo nombre)
  ([`../legal/BRECHAS-DE-DATOS.md`](../legal/BRECHAS-DE-DATOS.md)). El token de
  Supabase no puede leer datos de nadie (no lleva Database), pero sí cambiar
  el SMTP y las plantillas de Auth. El de Lettermint podría crear tokens que
  envían como `rwadar.app` y borrar el proyecto.
